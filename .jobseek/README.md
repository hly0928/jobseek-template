# JobSeek Runtime Control Plane

`.jobseek/batches/` is the runtime source of truth. `cache/` is a disposable index that can be rebuilt with `tools/jobseekctl rebuild-cache --track <track>`; it never establishes candidate facts.

A new batch's `inputs/` and `input_snapshot.json` preserve the configured Candidate Profile, Criteria, Track Profile, answer/content banks, CV, rules, skills, agents, schemas, and control code. Resume validates only those copies; later source edits affect only new batches. `events.jsonl` is the append-only source for state, review/approval, and gate events. `discovery_events.jsonl` rebuilds `discovery_state.json`, and `jobs/<job_key>/job_evidence_packet.json` is the sole non-overwritable evidence packet for a role. Sensitive values must not be written here.

`batch_sequence.json` stores the latest workspace-wide batch sequence. A new batch is allocated under an exclusive lock by `jobseekctl preflight --new-batch` and named `<track>-<Perth YYYYMMDD>-<sequence>`; the sequence is at least three digits and increases by exactly one. `--batch-id` only resumes an existing directory. Historical noncanonical directories remain unchanged and do not reset the sequence.

A modern Job Evidence Packet must include the complete saved advertisement, metadata, extracted facts and locations, duplicate checks, one evaluation for each frozen hard-exclusion rule, complete and correctly totaled score components, authority-registry fact IDs, stable inference IDs with all bounds, complete classification inputs, classification, risks, unresolved items, and artifact paths. `jobseekctl` reduces classification from the batch snapshot's hard-exclusion definitions, score components, and `eligible_threshold`; it rejects missing, contradictory, or indeterminate packets or classifies them as `Needs Review`. Legacy packets remain readable through compatibility paths. `metadata.track` and the job key must match the batch. Corrections require a new batch event and must not overwrite a packet.

Each track's executable hard-exclusion IDs and definitions, score components, and eligibility threshold live only in `.jobseek/config.json` under `tracks.<track>.assessment`. Search Criteria and Skills reference this frozen configuration and must not define a second executable policy.

Gate events accept only fixed actors and roles. Every new or resumable submission must follow `Package Prepared → Awaiting User Review → Submission Ready → Submitted`. Review binds the role, page, answers, attachments, and declarations; the lead may record approval only after the user explicitly approves that single role. Any bound evidence or material hash change invalidates approval. `record-gate` is limited to `materials_qa` and `submission_evidence`; eligibility and confirmation audits require their structured commands and cannot be auto-promoted through a compatibility gate. Stop counters are derived from events and discovery deltas; caller-supplied counters are accepted only as fully matching deprecated assertions.

Each `Needs Review` issue has a unique `reason_id`, fingerprint, and fixed set of allowed decisions. Runtime states are `pending|remain_paused|resolved|skipped`; `remain_paused` may later be resolved or skipped. A user-supplied answer, file, or declaration may resolve only the associated unresolved item. `continue` for an experience gap addresses only that non-mandatory gap and cannot clear another review reason or blocker. Eligibility audits append a versioned `pass|pass_with_warnings|fail` overlay naming each resolved reason, unknown rule, unresolved item, or standard blocker; the original packet is never overwritten.

Each final submission review creates a unique `submission_attempt_id`. Review, approval, submission evidence, and `Submitted` must use the same attempt; entering `Submitted` consumes the approval. After `Submitted → Failed`, return to `Awaiting User Review`, record the current page and materials again, and obtain new approval. Confirmation assessment, audit trigger, structured audit result, and gate must also use that attempt. Audit results are only `verified|not_submitted|unresolved`; only `not_submitted` may enter `Failed`. Count consecutive submission failures by final attempt result; an open `Submitted` attempt does not reset the sequence, and only `Submission Verified` interrupts it.

Legacy `Submitted → Blocked` states are recoverable only with the current attempt's post-submit state and continue through confirmation for that attempt. `unresolved` remains paused, cannot count as complete, cannot create a new attempt, and cannot finalize.

Eligibility triggers have immutable `trigger_id` values and monotonically increasing versions. The current trigger set is the stable union of packet-native and recorded event triggers. Audits and gates store the complete trigger set/version. New triggers, new evidence for a resolved trigger, or packet/evidence hash changes invalidate older gates; a new audit must cover every current trigger before materials or submission can continue.

Discovery frontiers complete normally only in `exhausted` or `saturated` state; `active` means searchable and `blocked` means paused pending recovery. After a stop target, run `discovery-drain` to idempotently record unclaimed candidates as `deferred_due_to_batch_stop` while retaining drain duties for claimed or opened advertisements. A modern `fully_assessed` candidate must uniquely link its URL, job key, validated packet, and a matching state at least `Assessed`; `validate`, counters, and finalization use the same link check.

An advertisement confirmed after full open as expired, unreadable, a known duplicate, or already applied must include a reason and evidence and map mechanically to `Expired`, `Withdrawn`, or `Duplicate`. It clears open work and normally does not count toward `fully_assessed_ads`.

Agent-call no-yield circuits are role-scoped. A total-budget, role-circuit, or per-role/job retry limit makes `check-stop` return a recoverable pause; only explicit user authorization lets the lead use `resume-agent-calls` to record a reset or bounded extension. The frozen policy remains intact, with calls reserved for drain, confirmation, and safe closeout.

Retry exhaustion means that the role or job still has unfinished work and the last permitted call failed, yielded nothing, or did not complete its objective. A productive final call that crosses the role's stage boundary does not trigger exhaustion. Schema-v1 batches without a manifest policy use `legacy_v1_defaults`; first resume creates batch-local compatibility facts and a safe agent project only when the manifest source hashes still match. Drift fails closed. Runtime-v1 batches likewise receive a one-time hashed safety upgrade; later track configuration, Skills, agent configuration, and control scripts are read from the batch-local runtime. `preflight` and `runtime-context` return `worker_runtime.project_root`, its environment, and `control_entrypoint` as the worker's only valid launch contract.

Submission-record archival first appends an attempt-scoped intent, then idempotently reconciles the archive, Tracker, and Run Log, and finally appends a completion event. After an interruption, retry the exact same request. `validate` applies the JSON schemas and checks cross-event attempt, gate, retry, frontier, and finalization invariants without silently modifying the batch.
